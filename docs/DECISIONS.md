- HU 18: la aceptación deja el pedido en `asignado`, registra la hora de aceptación y habilita la acción existente de retiro; `retirado` se conserva como transición posterior. Esta interpretación mantiene el criterio de aceptación y el flujo de estados implementado en el backend. Confirmar con el equipo si se requiere un estado distinto para la confirmación.
- HU 34 — Confirmación de devolución: decisión de implementación tomada a pedido del usuario el 2026-11-17 y limitada a HU 34. Se agrega `main.operario.Devolucion`, separada de `HistorialEstado`, con relación uno a uno con `Pedido`, operario y fecha/hora; el pedido conserva estado `fallido`. La pantalla HU 34 muestra en su propia cronología el evento de falla y la recepción; no se modifican las vistas compartidas de HU 14/33 ni HU 38. Un segundo POST es idempotente y conserva actor/fecha originales. La entidad bloquea edición y borrado por instancia y queryset, su relación protege el pedido y el usuario de borrados, y Django Admin no permite agregar, editar ni eliminar. Se eligió esta alternativa para evitar una transición falsa y no cambiar el modelo de eventos de otras historias. La decisión de una única confirmación interpreta “confirmar devolución” como cierre de una recepción física; si el proceso permite más de una, debe revisarse. En la exportación versionada, HU 19 describe transiciones de entrega y no menciona el retorno al centro; Entrevista 02 sí dice que el pedido Fallido vuelve al centro. El orden de HU 34 sigue siendo una propuesta: fecha del evento fallido ascendente (más antiguo primero), desempate por `pk` y, ante varios intentos, se muestra el último. La confirmación permanece fuera del seguimiento público.
- Para una futura migración productiva, ensayar el esquema contra una copia autorizada con pedidos heredados: en este entorno no existía una base poblada para validar sus datos reales.
