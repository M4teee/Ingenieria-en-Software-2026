## Datos y compatibilidad

- Los pedidos nuevos se relacionan con `Comercio`; `Pedido.repartidor` es opcional para que un pedido pueda existir antes de su asignación. `HistorialEstado` conserva estado anterior/nuevo, usuario, fecha, incidencia y archivo fotográfico.
- `Pedido.datos_destinatario` y `Pedido.tamano_paquete` son campos de texto con valor vacío predeterminado para mantener compatibles los pedidos anteriores. La migración `repartidor.0010` los agrega sin inferir valores históricos. `Pedido.vehiculo_requerido` pasó de `TextField` a `CharField` con las opciones de `Repartidor.VEHICULOS` en la migración `repartidor.0011`; la migración no reescribe los valores históricos, por lo que pedidos anteriores con texto libre o vacío conservan su valor y se muestran tal como están o como “No informado”.
- La migración `users.0004_user_is_operario` agrega el campo de rol, preserva el acceso operativo existente copiando `is_staff=True` a `is_operario=True` y deja ambos atributos independientes después de migrar. Las pruebas usaron una base temporal SQLite; no alteraron la base local configurada.
- La base local contiene datos de desarrollo preexistentes. No se alteraron ni usaron como evidencia funcional; la inspección del panel fue de solo lectura. La compatibilidad con una base productiva poblada no se validó.
- `Backend/config/settings.py` configura `DATABASES['default']` usando `dj_database_url.config(...)` con `conn_max_age=0`, `conn_health_checks=True` y las opciones `connect_timeout=5`, `keepalives=1`, `keepalives_idle=15`, `keepalives_interval=5`, `keepalives_count=3` y `pool={'min_size': 1, 'max_size': 5, 'timeout': 10.0, 'max_idle': 20.0, 'max_idle_seconds': 20.0}` cuando `DATABASE_URL` está configurado con PostgreSQL (Neon). `conn_max_age=0` devuelve las conexiones al pool propio al finalizar cada petición; `config/pool.py` implementa `SimpleConnectionPool`, un pool thread-safe liviano que reutiliza conexiones abiertas entre peticiones de distintos hilos sin volver a pagar el handshake SSL/TLS en cada clic. Para evitar errores por caídas remotas (`psycopg.OperationalError: consuming input failed: SSL connection has been closed unexpectedly`) cuando PgBouncer/Neon cierra conexiones inactivas del lado del servidor, el pool rastrea la antigüedad de inactividad de cada conexión mediante `max_idle_seconds` (20 s), cerrando y descartando proactivamente conexiones que hayan superado ese umbral para abrir una fresca, y realiza un sondeo no bloqueante con `select()` y `consume_input()` sobre el socket para detectar paquetes de cierre TCP (FIN/RST) antes de reutilizar cualquier conexión. Además, resuelve dinámicamente la dirección IPv4 del host de Neon y la asigna a `OPTIONS['hostaddr']`: en Windows sin ruteo IPv6 funcional, `getaddrinfo` devolvía direcciones IPv6 sin ruteo funcional en el entorno, y `hostaddr` permite conectar por IPv4 preservando `host` para SNI y TLS.
- Reducción de round-trips a la base remota: `settings.py` activa `SESSION_ENGINE = 'django.contrib.sessions.backends.cached_db'` con `LocMemCache`, eliminando la consulta recurrente a `django_session` en cada petición. `main.users.backends.CachedModelBackend` cachea la consulta de `get_user` en memoria local durante 300 s con invalidación inmediata por señales `post_save` y `post_delete` de `User`, eliminando la consulta recurrente a `users_user` en cada petición.
- Optimización de vistas y consultas: `main.repartidor.views._exigir_repartidor_activo` aprovecha la relación inversa `usuario.repartidor` poblando su caché interna, lo cual evita consultas redundantes al perfil de repartidor tanto en las vistas como en el renderizado de `base.html`. En `repartidor.views.home`, se unificaron las consultas de pedido asignado pendiente y pedido activo en una sola consulta con `select_related('comercio')`. La migración se aplicó tanto a SQLite local como a Neon PostgreSQL.
- `main.despacho.procesar_asignaciones_vencidas` ejecuta primero una consulta liviana `exists()` sobre pedidos `asignados` con `fecha_hora_asignacion <= limite` antes de abrir transacciones o iterar, evitando bloqueos y aperturas transaccionales innecesarias en cada carga de vista.
